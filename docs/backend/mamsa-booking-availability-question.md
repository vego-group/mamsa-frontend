# سؤال — هل التواريخ المحجوزة محمية فعليًا من التعارض؟

**Date:** 2026-08-27 · From: Next.js (www) · **Status:** طلب — يحتاج تأكيد + مقترح تحسين

مصدر الطلب: مراجعة رحلة الحجز بالكامل (`date-range-picker.tsx`، `units/[id]/page.tsx`،
`booking/[unitId]/checkout-page-client.tsx`) بعد سؤال من المالك: الأيام اللي اتحجزت، ممكن تظهر
تاني لضيف تاني ويحجزها؟

الـ surface المقصود: user app، Bearer، `https://api.mamsaa.com/api/v1`.

---

## 1. اللي موجود عندنا دلوقتي

الفرونت إند مالوش أي مصدر بيانات لـ «الأيام المحجوزة» لوحدة معيّنة. مفيش endpoint بيرجّع تقويم أو
نطاقات محجوزة، ومفيش حقل زي `blocked_dates` على مورد الوحدة. النتيجة:

- كاليندر صفحة البحث (`src/components/ui/date-range-picker.tsx:294`) بيعطّل بس الأيام اللي فاتت:
  ```ts
  const disabled = iso < min;
  ```
- حقول التاريخ في صفحة الوحدة (`src/app/units/[id]/page.tsx:371-388`) نفس المبدأ — `min`/`max`
  بس بين تاريخ الوصول والمغادرة، بدون أي وعي بحجوزات موجودة فعلاً.

يعني أي زائر بيفتح صفحة وحدة محجوزة من ٥ لـ ١٠ الشهر مثلاً، هيلاقي الأيام دي شكلها عادي وقابلة
للاختيار — مفيش أي إشارة بصرية إنها مش متاحة.

الفحص الوحيد بيحصل متأخر: عند الـ checkout بس (`checkout-page-client.tsx:82-86`)، بننادي:

```
POST /units/{id}/availability   { start_date, end_date }
```

ولو رجع `available: false` بنوقف الحجز برسالة (`errors.unitUnavailable`) ونرجّع الضيف لصفحة
الوحدة. يعني الضيف بيوصل لآخر خطوة قبل الدفع — بعد ما يملا بياناته الشخصية — عشان يكتشف إن
التواريخ مش متاحة.

---

## 2. التأكيد المطلوب فورًا (الأهم — مفيش كود مطلوب بالضرورة، بس تأكيد)

إحنا مش شايفين كود الباك إند، فمش قادرين نتأكد إن:

1. `POST /units/{id}/availability` فعليًا بيقارن بالحجوزات اللي حالتها `confirmed`
   (وممكن `pending_payment` كمان، لو فيه حجز تاني لسه ماسك نفس التواريخ)، مش بس بيرجّع
   `available: true` ثابت.
2. `POST /bookings` (إنشاء الحجز) **بيعيد نفس فحص التوفر من جديد وقت الإنشاء**، مش بس بيثق إن
   الفرونت إند نادى `availability` قبلها ورجعت `true`. لو مفيش فحص وقت الإنشاء، فيه احتمال
   race condition: ضيفين يفتحوا checkout لنفس الوحدة في نفس اللحظة، الاتنين يعدّوا فحص التوفر
   (لسه محدش حجز فعليًا)، وبعدين الاتنين ينجحوا في إنشاء حجز بنفس التواريخ.
3. لو فيه حماية من الـ race condition دي على مستوى الداتابيز (unique/exclusion constraint على
   نطاق التواريخ لكل وحدة، أو row locking وقت الإنشاء) — مش بس منطق تطبيقي عادي ممكن ينفلت تحت
   حِمل متزامن.

**المطلوب:** تأكيد كتابي إن الثلاث نقط دي متغطية. لو مش متغطية، نحب نعرف عشان نقرر إزاي نتعامل
معاها من عندنا (رسالة أوضح، إعادة محاولة، … إلخ).

---

## 3. مقترح تحسين — تقويم توفر بدل الاكتشاف المتأخر

الوضع الحالي (الاكتشاف بس عند الـ checkout) شغال كحماية أخيرة، بس تجربة سيئة: ضيف يختار تواريخ،
يملا بياناته، يوصل لآخر خطوة، وبعدين يتفاجئ إنها مش متاحة.

**المقترح:** endpoint يرجّع نطاقات الأيام المحجوزة لوحدة معيّنة، مثلاً:

```
GET /units/{id}/blocked-dates?from=2026-09-01&to=2026-12-31
```

```json
{
  "blocked": [
    { "start": "2026-09-05", "end": "2026-09-10" },
    { "start": "2026-09-20", "end": "2026-09-22" }
  ]
}
```

لو ده متاح، هنعطّل الأيام دي مباشرة في الكاليندر (بنفس منطق تعطيل الأيام اللي فاتت الموجود
حاليًا) — الضيف يشوف بس الأيام المتاحة فعليًا من أول لحظة، بدل ما يكتشف التعارض في آخر خطوة.
