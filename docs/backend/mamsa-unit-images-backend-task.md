# Task — صور الوحدات: مقاسات ثابتة + قيود الرفع

**Date:** 2026-08-26 · From: Next.js (www) · **Status:** طلب — لسه ما اتنفذ شي

الـ surface المقصود: user app، Bearer، `https://api.mamsaa.com/api/v1` — مورد الوحدة (`GET /units/{id}` و `GET /units`).

---

## 0. الخلفية — إيش اتصلّح عندنا وإيش الباقي عندكم

ظهر باج في `mamsaa.com/units/35`: شريط الصور المصغّرة في العارض الكامل (lightbox) يختفي تحت حافة الشاشة لما تكون الصورة طولية. **الباج ده اتصلّح عندنا** — كان خطأ CSS في `UnitGallery.tsx`، ما له علاقة بالـ API، وما نحتاج منكم شي عشانه.

بس أثناء التشخيص طلعت مشكلتين ما نقدر نحلّهم من طرف الواجهة، وهم موضوع الطلب ده:

1. **الأداء** — مورد الوحدة يرجّع رابط واحد لكل صورة، والواجهة تستخدم نفس الرابط في خمس مقاسات مختلفة (من 64×64 لحد ملء الشاشة).
2. **اتساق النِسَب** — ما في أي قيد على أبعاد الصورة عند الرفع، فالشريك يقدر يرفع أي شي.

## 1. المشكلة — رابط واحد لكل الاستخدامات

الشكل الحالي اللي يوصلنا (`RawImage` في `src/lib/api/adapters.ts:32`):

```json
"images": [
  { "id": 91, "url": "https://api.mamsaa.com/storage/units/35/a1b2.jpg", "is_main": true }
]
```

وين نستخدم الرابط ده بالظبط:

| المكان | المقاس المعروض فعلياً | الملف |
|---|---|---|
| شريط المصغّرات في الـ lightbox | 96×64 | `UnitGallery.tsx:152` |
| مصغّرة ملخّص الحجز | 64×64 | `checkout-page-client.tsx:335` |
| كارت الوحدة (بحث / رئيسية) | ~400×300 | `UnitCard.tsx:36` |
| الـ collage في صفحة الوحدة | حتى 800×440 | `UnitGallery.tsx:70,79` |
| العارض الكامل (lightbox) | ملء الشاشة | `UnitGallery.tsx:132` |

**النتيجة اليوم:** وحدة فيها 6 صور، كل صورة ~2–4MB → فتح الـ lightbox يحمّل 12–24MB على بيانات الموبايل، ومصغّرة 96×64 تنزّل نفس الملف الكامل بتاع الـ 4MB. صفحة البحث فيها 12 كارت = نفس المشكلة مضروبة في 12.

ده مش شي نقدر نحسّنه من الواجهة — الحل الوحيد إن السيرفر يرجّع نسخ جاهزة بمقاسات أصغر.

## 2. المطلوب — نسخ ثابتة (derivatives) لكل صورة

تتولّد **مرة واحدة عند الرفع** (queue job)، مش on-the-fly مع كل request:

| المفتاح | المقاس | الطريقة | يستخدم في |
|---|---|---|---|
| `thumb` | 400×300 | cover — قص لـ 4:3 | المصغّرات + مصغّرة الحجز |
| `card` | 800×600 | cover — قص لـ 4:3 | كروت البحث + الـ collage |
| `full` | أطول ضلع 2048 | contain — **بدون أي قص** | العارض الكامل |
| `original` | كما هي | — | الأرشيف / لوحة الأدمن |

**مهم:** `full` بدون قص إطلاقاً. في العارض الكامل الضيف لازم يشوف الصورة كاملة زي ما رفعها الشريك — أي قص هنا معناه إخفاء جزء من الوحدة قبل الحجز. القص مسموح بس في `thumb` و `card` عشان الشبكة تطلع مرتّبة.

### شكل الـ response المطلوب

```json
{
  "id": 91,
  "url": "https://api.mamsaa.com/storage/units/35/a1b2.jpg",
  "is_main": true,
  "width": 1600,
  "height": 2400,
  "variants": {
    "thumb": "https://cdn.mamsaa.com/units/35/a1b2_thumb.webp",
    "card":  "https://cdn.mamsaa.com/units/35/a1b2_card.webp",
    "full":  "https://cdn.mamsaa.com/units/35/a1b2_full.webp"
  }
}
```

**ما في breaking change:** خلّوا `url` زي ما هو. عندنا هيفضل fallback لو `variants` ناقصة أو الصور القديمة لسه ما اتعالجت، فتقدروا تنشروا التغيير على مراحل.

### ملاحظات تنفيذ

- **`width` / `height` مطلوبين حتى لو أجّلتوا الـ variants.** نستخدمهم عشان نحجز مساحة الصورة قبل ما تنزّل (يمنع الـ layout shift / CLS) ونعرف الصورة الطولية من العرضية قبل التحميل. دول حقلين رخاص جداً — صفّهم في جدول الصور عند الرفع.
- WebP كصيغة أساسية + JPEG fallback لو سهل. جودة ~82 كفاية.
- أسماء الملفات deterministic (نفس الـ hash + suffix) عشان نقدر نبني الرابط بنفسنا لو احتجنا.
- **بديل مقبول:** لو تفضّلوا image proxy بدل ملفات ثابتة (زي `imgproxy` أو Cloudflare Images)، تمام برضه — بس نحتاج المقاس في الرابط نفسه، زي ما بوكينج عاملها:
  `cdn.mamsaa.com/units/35/a1b2.jpg?w=400&h=300&fit=cover`
  المهم إن الواجهة تقدر تطلب مقاس محدد، مش إن الطريقة تكون ملفات ثابتة بالذات.
- في لارافيل: `Intervention/Image` v3 أو `spatie/laravel-medialibrary` بالـ conversions — الاتنين يعملوا ده جاهز.

## 3. قيود الرفع (validation) — عند إضافة/تعديل الوحدة

| القيد | القيمة | السبب |
|---|---|---|
| حد أدنى للدقة | 1280×720 | أقل من كده تطلع مهزوزة في الـ lightbox — ترفض بـ 422 برسالة واضحة للشريك |
| حد أقصى لحجم الملف | 10MB | |
| الصيغ | `jpeg`, `png`, `webp`, `heic` | **HEIC مهم** — الآيفون يصوّر بيها افتراضياً، ولو ما تتحوّل لـ JPEG/WebP الصورة ما تظهر أصلاً في المتصفح |
| النسبة (aspect ratio) | من 3:4 (طولي) لـ 16:9 (عرضي) | خارج المدى ده ترفض، أو تُقص لـ 4:3 وقت توليد `thumb`/`card` |

### حاجتين لازم يتعملوا وقت المعالجة

1. **تطبيق EXIF orientation قبل الحفظ.** صور الآيفون كتير تتخزّن مقلوبة مع flag اتجاه — لو الـ flag ما اتطبّق على البكسل نفسه، الصورة تطلع مقلوبة في المتصفح. لازم تتطبّق وتتشال.
2. **تنظيف باقي الـ EXIF، خصوصاً GPS.** صور الشريك فيها إحداثيات الوحدة الحقيقية بالمتر. ما ينفع تتسرّب في ملف عام — ده تسريب بيانات فعلي.

## 4. تحسينات مطلوبة بس مش عاجلة

- **`sort_order`** على الصورة. حالياً إحنا نرتّب بـ `is_main` بس، والباقي بترتيب الـ API كما هو — فالشريك ما يقدر يتحكّم في ترتيب عرض صوره.
- **`alt`** — وصف قصير للصورة (SEO + قارئ الشاشة). حالياً نولّد `"{اسم الوحدة} 3"` من طرفنا.
- **CDN** على روابط الصور بدل `api.mamsaa.com/storage` مباشرة.

## 5. اللي **ما** نحتاجه — AI enhancement / upscaling

اتناقشنا في ربط خدمة AI تعمل resize + enhancement للصور، **وقرّرنا نستبعدها**، عشان لو الفكرة جت من ناحيتكم برضه:

- صور الوحدة محتوى تعاقدي — الضيف يحجز بناءً عليها. أي upscaling أو enhancement بالـ AI **يخترع تفاصيل مش موجودة** (يوضّح خشب مش بالنضافة دي، يظبّط إضاءة غرفة ضلمة). ده تضليل للضيف ومسؤولية على المنصة.
- تكلفة و latency على كل صورة مرفوعة، بدون مقابل حقيقي.
- ولا بوكينج ولا إيربنب يعملوا كده — يعتمدوا resize عادي + شروط دقة عند الرفع، وهو اللي طالبينه في §2 و §3.

الـ resize العادي بمكتبة صور عادية يدّي نتيجة نضيفة 100%، فوري، وببلاش.
