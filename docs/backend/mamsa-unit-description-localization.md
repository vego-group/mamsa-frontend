# وصف الوحدة بلغتين — طلب حقل مترجَم

**الحالة:** الواجهة جاهزة للعرض بلغتين، والباك-إند لا يرسل إلا نصًّا واحدًا.
**المطلوب:** ترجمة `description` (و`name`) لكل وحدة، وإرسال نسخة اللغة المطلوبة.
**من:** فريق `mamsa-app` (الموقع العام). **إلى:** فريق الـ API + فريقا اللوحتين.

---

## الأثر اليوم

الموقع يعمل بلغتين (`ar` / `en`)، وكل نصّ من عندنا مترجَم في
`messages/{ar,en}.json`. أما ما يكتبه الشريك — عنوان الوحدة ووصفها — فيأتي من
`GET /units/{id}` في حقل واحد:

```json
{ "name": "شقة بغرفة نوم واحدة", "description": "تتكوّن الشقة من غرفة نوم واحدة…" }
```

فالضيف الذي يفتح النسخة الإنجليزية يقرأ واجهة إنجليزية بالكامل ثم يصل إلى قسم
**About this place** فيجده عربيًّا. لا خطأ في الترجمة عندنا: لا توجد نسخة
إنجليزية أصلًا لنعرضها.

## ما عالجناه من طرفنا (لا ينتظر شيئًا منكم)

النصّ العربي داخل الصفحة الإنجليزية كان يُعرض بالاتجاه واللغة والخطّ الخطأ.
الآن الواجهة تستنتج ذلك من النصّ نفسه لا من لغة الصفحة
(`detectTextDirection` في `src/lib/utils/rich-text.ts`):

- **الاتجاه:** بغلبة الحروف العربية على اللاتينية → `dir="rtl"`، فتعود النقطة
  إلى آخر السطر وتعود نقاط القوائم إلى اليمين.
- **اللغة:** `lang="ar"` لينطقها القارئ الصوتي بصوت عربي.
- **الخطّ:** `font-arabic` — الصفحة الإنجليزية تُحمّل Inter وحده، وهو خطّ بلا
  حرف عربي واحد، فكان النصّ يسقط على خطّ النظام الاحتياطي.

هذا يجعل الوصف العربي **مقروءًا** في الصفحة الإنجليزية، ولا يجعله **مترجَمًا**.

## العقد المقترح

الترتيب حسب الأفضلية. أيّ واحد منها يكفي، ولا نحتاج أكثر من واحد:

### ١) `Accept-Language` (المفضَّل)

يبقى شكل الاستجابة كما هو حرفيًّا، ويردّ الـ API نسخة اللغة المطلوبة:

```http
GET /api/v1/units/37
Accept-Language: en
```

```json
{ "name": "One-bedroom apartment", "description": "A spacious one-bedroom apartment…" }
```

- الترويسة **مأمونة في CORS** (safelisted) فلا تُحدث preflight جديدًا ولا تمسّ
  إعدادات `config/cors.php`.
- لا تغيير في `adapters.ts` ولا في أنواع `@/types` عندنا.
- **الارتداد إلزامي:** وحدة بلا ترجمة إنجليزية تعيد العربية كما هي، لا نصًّا
  فارغًا. الحقل الفارغ يعني عندنا «لا وصف» فيختفي القسم كاملًا.
- نُرسل الترويسة من `http()` في `src/lib/api/client.ts` فور تأكيدكم الدعم.
  لن نرسلها قبل ذلك: ترويسة يتجاهلها الـ API اليوم ثم يبدأ تفسيرها غدًا تغيّر
  سلوك الموقع دون نشر من طرفنا.

### ٢) حقول صريحة لكل لغة

```json
{
  "name": "شقة بغرفة نوم واحدة",
  "name_en": "One-bedroom apartment",
  "description": "تتكوّن الشقة…",
  "description_en": "The apartment consists of…"
}
```

يبقى `name` و`description` كما هما (توافق خلفي كامل)، وتُضاف `*_en` اختيارية.
نختار نحن حسب لغة الصفحة ونرتدّ إلى الأصل عند الغياب.

### ٣) خريطة ترجمات

`{"description": {"ar": "…", "en": "…"}}` — مقبول، لكنه يكسر شكل الحقل الحالي
ويحتاج نشرًا متزامنًا من الطرفين. لا نرشّحه.

## ما يلزم في اللوحتين

- حقل وصف ثانٍ (إنجليزي) **اختياري** في نموذج الوحدة — لوحة الشريك ولوحة
  الأدمن (`/units/new` والمراجعة).
- نفس علامات التنسيق البسيطة تنطبق على النسختين بلا فرق
  (`docs/backend/mamsa-unit-description-formatting.md`).
- ترك الحقل فارغًا سلوك سليم لا خطأ: الضيف يرى العربية.

## ملاحظات

- **العنوان أهمّ من الوصف** إن اضطررتم للترتيب: `name` يظهر في نتائج البحث
  والبطاقات والحجز والفاتورة، فبقاؤه عربيًّا في صفحة إنجليزية أكثر ظهورًا.
- **لا ترجمة آلية عند العرض.** الوصف بند تعاقدي يقرؤه الضيف قبل الدفع، وترجمة
  آلية صامتة تحوّل خطأ ترجمة إلى نزاع حجز. الترجمة تُكتب وتُراجَع مرة واحدة عند
  الإدخال، لا في كل طلب.
- **الأسماء العربية للمرافق** ليست جزءًا من هذا الطلب: `amenities[].key` مفردات
  مغلقة نترجمها عندنا في `messages/*.json` (`explore.filters.amenities.*`).
  المطلوب فقط ألّا تتغيّر تلك الـ slugs.
